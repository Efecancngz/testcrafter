# Bot Challenge Detection — Design

**Date:** 2026-08-13
**Status:** Approved

## Problem

`extract_page_structure` (`backend/app/crawler.py`) treats any page that
`page.goto()` successfully loads as scannable content. When the target URL
serves a bot-verification challenge (Cloudflare "Just a moment...",
reCAPTCHA, hCaptcha) instead of the real page, `page.goto()` still succeeds
— there's no network error, so `create_scan`'s existing
`except PlaywrightError` never fires. The crawler extracts whatever
elements the challenge page happens to have (often near-empty or
nonsensical), the AI provider generates scenarios from garbage input, and
the scan proceeds as if it succeeded. The user sees a confusing failure (or
a "successful" scan with meaningless scenarios) with no indication the
actual cause was a bot check.

## Goal

Detect known bot-verification challenge pages during crawl and stop the
scan immediately with a distinct, user-legible status — instead of letting
challenge-page content flow into scenario generation.

## Detection approach

Signature-based detection only (no content-density heuristics — those risk
false positives on genuinely sparse legitimate pages). Runs in
`extract_page_structure`, immediately after `page.goto()`, before element
extraction. Checks in this order, first match wins:

1. **Response header** — `response.header_value("cf-mitigated")` present →
   `"cloudflare"`
2. **Page title** — matches a known challenge title
   (`"Just a moment..."`, `"Attention Required! | Cloudflare"`) →
   `"cloudflare"`
3. **DOM markers** — first matching selector wins:
   - `iframe[src*="recaptcha"]` → `"recaptcha"`
   - `iframe[src*="hcaptcha"]` → `"hcaptcha"`
   - `[class*="cf-turnstile"], iframe[src*="challenges.cloudflare.com"]` →
     `"cloudflare"`

If none match, proceed with normal element extraction exactly as today.

## Data flow

`crawler.py` gains a new exception:

```python
class BotChallengeDetected(Exception):
    def __init__(self, provider: str):
        self.provider = provider
```

`extract_page_structure` raises it as soon as a signature matches — before
running the existing `_SELECTORS` extraction loop.

`backend/app/models.py`: `Scan` gains `blocked_reason: Mapped[str | None]`
(nullable, no default). New Alembic migration (autogenerated via
`alembic revision --autogenerate`, following the project's established
migration workflow — no manual edits to the generated file).

`backend/app/api/scans.py`: `create_scan`'s existing try/except around
`extract_page_structure` gains a new branch, checked before the existing
`except PlaywrightError` (order matters only for clarity — the two
exception types don't overlap, `BotChallengeDetected` does not subclass
`PlaywrightError`):

```python
except BotChallengeDetected as e:
    logger.info("bot challenge detected for scan %s (%s): %s", scan.id, payload.target_url, e.provider)
    scan.status = "blocked"
    scan.blocked_reason = e.provider
    session.commit()
    session.refresh(scan)
    return ScanOut(id=scan.id, target_url=scan.target_url, status=scan.status, blocked_reason=scan.blocked_reason, scenarios=[])
except PlaywrightError:
    ...  # unchanged
```

`ScanOut` (in `scans.py`) gains `blocked_reason: str | None = None`. The
`get_scan` endpoint's return also includes it (already constructs
`ScanOut` from the same fields — one-line change).

## Frontend

`Scan` status handling gains a `"blocked"` case, distinct from `"failed"`:
shown with a warning (not error) treatment and the message
`"This site uses {blocked_reason} bot protection and couldn't be scanned."`
(English primary, per project convention — Turkish string added to
whatever i18n/copy location the existing failed-state message uses, if
any exists; otherwise plain English matching current frontend state).

This is the only frontend change in scope for this feature. A broader
frontend redesign is a separate, future conversation (per user direction)
and explicitly out of scope here.

## Testing

New fixture pages under `backend/tests/fixtures/` (following the existing
`file://`-based crawler test pattern):
- `cloudflare_challenge.html` — title `"Just a moment..."`, no real
  content
- `recaptcha_challenge.html` — contains an `iframe` with
  `src` containing `recaptcha`

Tests:
- `extract_page_structure` raises `BotChallengeDetected(provider="cloudflare")`
  for the Cloudflare fixture (title match)
- `extract_page_structure` raises `BotChallengeDetected(provider="recaptcha")`
  for the reCAPTCHA fixture (DOM match)
- `extract_page_structure` behaves unchanged (no exception, normal
  extraction) for existing non-challenge fixtures — regression guard
- `create_scan` integration test: mocked `extract_page_structure` raises
  `BotChallengeDetected("cloudflare")` → response has
  `status="blocked"`, `blocked_reason="cloudflare"`, `scenarios=[]`, and
  the AI provider is never called (mock assert not called)

Header-based detection (`cf-mitigated`) is not covered by a fixture test
since `file://` navigation has no HTTP response headers — it's exercised
only by the real Cloudflare-serving integration path, which this project
doesn't test against live third-party sites (consistent with existing
"AI adapters and crawler use mocked responses/pages" testing convention
in `CLAUDE.md`). This is a known, accepted gap: the header check is
simple enough (single `header_value` call, direct string comparison) that
the risk of an untested regression is low relative to the cost of
mocking Playwright's `Response` object.

## Out of scope

- Content-density heuristics (rejected — false-positive risk on sparse
  legitimate pages)
- Any bypass/retry mechanism for challenge pages (this feature detects and
  stops, it does not attempt to solve or work around the challenge)
- Frontend redesign beyond the one new status treatment (separate future
  work, per user direction)
